## 2. 수치·운영 기본값

아래 수치는 사용자에게 제안한 출발값과 구현을 위한 기본 결정이다. 학습 효과가 검증된 수치가 아니며, 상수로 한곳에 모은다. 근거 있는 변경은 WORK_LOG에 기록한다.

| 항목 | 기본 결정 |
| --- | --- |
| 생성 틈새 카드 | 학습자 전체 과목 합산, 현지 날짜당 신규 승인 최대 3장 |
| 생성 카드 덱 비율 | 실제 최종 덱 길이 N 기준 `floor(N * 0.20)` 이하. N<5면 생성 카드 0장 |
| 확인 문제 | 학습자 전체 과목 합산, 날짜당 신규 승인 최대 1개, 실제 출제 최대 1개 |
| 확인 문제 분량 | 기존 하루 목표 안의 한 문제를 대체. 목표 달성 뒤 별도로 강요하지 않음 |
| 생성 작업 | 앱 foreground에서만 수행. 닫힌 앱에서 SIWC를 주기 호출하지 않음 |
| 자동 작업 횟수 | 날짜당 파이프라인 시도 최대 2회. 같은 입력의 성공 작업은 다시 실행하지 않음 |
| 작업 1회 호출 수 | 메모리 추출 1회 + 후보 생성 1회 + 별도 근거 검토 1회, 최대 3회. 7일 계획·사용자 채팅은 별도 |
| 자동 재시도 | 즉시 재시도 없음. 일시 오류만 10분 이후 다음 foreground/idle 기회에, 위 일일 한도 안에서 1회 |
| 메모리 입력 | 최근 14일 미처리 오답 최대 20개, 관련 개념의 완료 대화 최대 20개 메시지·총 8,000자 |
| 메모리 수 | 학습자·과목·개념별 활성/후보 합계 최대 3개 |
| 계획에 전달할 메모리 | 현재 과목의 active 최대 10개. 원문 대화 대신 요약·근거 종류·최근 시각·상태 |
| 생성 카드 수명 | 승인 후 14일까지만 신규 덱 편입. 숨김/만료 후에도 과거 채점 원본은 보존 |
| 확인 문제 시점 | 해당 개인화 카드에 실제 응답한 시각으로부터 24시간 이상 뒤, 다른 현지 날짜 |
| 메모리 오래됨 | 새로운 근거/확인 없이 30일 지나면 archived. 해결됐다고 표시하지 않음 |

한도는 SQLite에 저장해 앱 재실행·과목 왕복으로 초기화되지 않게 한다. 실제 dispatch 전에 호출 횟수를 예약하고, 승인 수와 출제 수는 각각 저장 트랜잭션에서 갱신한다. 날짜/시간대는 현지 일자+당시 timezone으로 저장하며 날짜를 되돌렸다고 기존 한도 행을 지우지 않는다. 원격 시간 검증은 도입하지 않는다.

## 3. 사용자가 경험하는 흐름

예시(실제 생성 결과를 보장하는 문구가 아님):

1. 앱의 스택·큐 문제에서 잘못된 보기를 고른다. 원래 채점·설명을 먼저 완료한다.
2. “큐도 나중에 넣은 게 먼저 나오나요?”라고 질문한다. 채팅 응답이 완전히 끝난 후 근거 후보를 만든다.
3. AI는 주어진 기록에서 “스택과 큐의 꺼내는 순서를 혼동했을 가능성”을 추출한다. 새 기록 없는 단순 재방문은 근거가 아니다.
4. 검토된 기준 자료를 사용해 짧은 O/X를 생성·검사·저장한다. 다음 덱 갱신 때 기존 카드와 섞는다.
5. 사용자는 잠금 화면에서 답한다. 네이티브 이벤트가 앱 재진입 시 SQLite에 한 번 반영된다.
6. 24시간 이상 지나 다음 학습을 할 때, 오늘 분량 안에서 다른 상황의 확인 문제 하나를 만난다.
7. 결과에 따라 헷갈림의 우선순위를 조절하고 다음 계획·덱에 반영한다. 정답 1회로 “완전히 이해함”을 선언하지 않는다.

신규 화면이나 채팅 탭을 추가하지 않는다. 기본 학습 중에는 생성 대기 스피너를 띄우지 않는다. 상세 메모리·근거는 개념 화면의 작은 진입점 뒤에 둔다.

## 4. 헷갈림 메모리: 관찰과 해석을 분리

### 4.1 저장할 근거

- 앱 오답: attempt ID, quiz ID/버전, 개념 ID, 실제 선택 보기, 정답 보기, 응답 시각, isGraded.
- 틈새/다시 풀기: 원래 문제 ID/버전과 실제 응답 이벤트 ID. 같은 이벤트 재수집은 같은 근거다.
- 대화: 학습자의 발언과 직전 맥락. assistant의 설명 자체를 사용자 오개념의 증거로 삼지 않는다.
- 단순 “예시 보여줘”, “왜 그래?”는 부족하다. 명시적 잘못된 주장/짝 비교 또는 오답과 연결되는 맥락이 있어야 한다.
- 실패·취소·스트리밍 중 대화, 중복 이벤트, 같은 문제 연속 탭을 새로운 근거로 세지 않는다.

현재 attempts 테이블에는 `selectedOptionId`가 있지만 `LearningSnapshot.Attempt`에는 없다. 메모리용 전용 repository 조회에서 선택 보기까지 읽는다. snapshot의 정답률만으로 추측하지 않는다.

### 4.2 메모리 상태

| 상태 | 진입/전이 규칙 |
| --- | --- |
| candidate | 오답 1회 등 약한 근거. 계획·자동 생성에는 아직 쓰지 않음 |
| active | 서로 다른 문제의 일치하는 오답 2건, 또는 다른 날짜의 동일 오답, 또는 맥락이 명확한 학습자 발언으로 오개념이 확인된 경우. AI 제안과 로컬 근거 검사를 모두 통과 |
| improving | 이 메모리를 겨냥한 확인 문제에서 유효한 정답 1회. 틈새 정답만으로 전환하지 않음 |
| resolved | 다른 날짜·다른 문제인 확인 문제/명시적으로 같은 오개념을 평가하는 기준 문제에서 유효한 정답 2회, 그 사이 대응 오답 없음 |
| archived | 사용자가 메모리를 삭제/무시하거나 30일간 새 근거 없음. resolved와 다름 |

- improving/resolved 후 같은 오개념을 겨냥한 유효 오답이 생기면 active로 복귀한다.
- 일반적인 같은 개념 문제를 맞혔다는 이유만으로 특정 오개념을 해결 처리하지 않는다. `memoryId/skillKey` 연결이 필요하다.
- 문구는 “~를 혼동했을 가능성”, “확인 중”처럼 근거 수준에 맞춘다. 성격·지능·학습 능력 평가를 저장하지 않는다.
- AI confidence 숫자를 사실 확률처럼 사용하지 않는다. 상태 전이·횟수는 앱 코드가 계산한다.
- 사용자가 메모리를 무시하면 그 근거 ID 묶음으로 재생성하지 않는다. 이후의 새 근거로만 후보를 만들 수 있다.

## 5. 생성 범위와 기준 자료

### 5.1 V4 최초 허용 범위

처음에는 `info-basic`의 `ds-stack`, `ds-queue`, `db-primary`, `db-foreign` 네 개념만 생성 후보로 삼는다. **이 목록은 즉시 검증 완료 목록이 아니다.** C1에서 기준 자료를 대조하고 해당 사실만 approved로 만든다. 나머지 개념과 SQLD는 기존 학습·채팅·계획을 유지하되 생성은 하지 않는다. 첫 버전에서 전체 72개 개념으로 자동 확장하지 않는다.

확인할 1차 자료 후보(내용을 실제 읽고 범위를 검증해야 함):

- 스택·큐: Python 공식 자료구조 튜토리얼의 stack/queue 설명.
- 기본키·외래키: PostgreSQL 공식 constraints 설명. “외래키가 언제나 기본키만 참조한다” 등 과도한 일반화 금지. DBMS별 차이가 있으면 문제 범위를 명시하거나 제외.

현재 catalog의 `reviewStatus=ai-draft`, `checkedAt=출처 대조 전`은 승인 근거가 아니다. 기존 문자열을 날짜로 바꾸기만 해서 approved 처리하지 않는다.

### 5.2 기준 자료 묶음

새 `src/data/content/generation-basis.json`에 conceptId, basisId, version, factId, 정리된 사실, 적용 조건, 출처 URL/절, 실제 확인 날짜, 승인 상태를 둔다. 긴 원문을 복사하지 말고 사실을 요약한다. 공식 자료와 대조한 사실을 개발 기록으로 남기며 사람 전문가 검수 완료라고 표시하지 않는다.

오개념 단위를 제한하기 위해 `skillKey`와 해당 factId를 기준 자료에서 정의한다. 예: 스택/큐의 꺼내는 순서. AI는 이 목록에서 선택하고 새 개념 ID/skillKey/출처 URL을 만들 수 없다. 자료를 확보하지 못한 개념은 생성 제외 상태로 유지하고 다른 개발을 계속한다.

### 5.3 생성·검토 과정

1. 로컬에서 허용된 개념·active/improving 메모리·해당 fact만 선택한다.
2. AI에 그 범위 안의 O/X 후보 최대 3개와 필요한 확인 문제 최대 1개를 요청한다. 후보는 근거 factId와 이유를 함께 반환한다.
3. 로컬 구조 검사: 알려진 ID, 길이, O/X 선택지, 4지선다의 유일한 정답, 중복, 허용 문자/내용을 검사한다.
4. 별도 검토 호출에 **문제·기준 사실·조건**을 제공한다. 생성자의 정답은 숨기고 독립 정답, 근거 factId, `supported/contradicted/ambiguous/unsupported`를 받는다.
5. 기준과 비교 가능한 답, 생성자/검토자 답 일치, 구조 검사 모두 통과한 후보만 승인한다. 애매함·근거 부족·검토 실패는 폐기하고 기본 콘텐츠를 사용한다.

두 AI의 동의는 진실 보증이 아니다. 자동 검토 통과와 전문가 검수를 구분한다. 근거 없는 자기 수정의 한계에 관한 참고: https://arxiv.org/abs/2310.01798 (기존 연구이며 현재 모든 모델에 동일 성능을 주장하는 근거로 쓰지 않는다).

잠금 화면 O/X는 **prompt 자체가 짧아야 한다.** V4 생성 카드의 short는 prompt와 같게 두어 축약문만 다른 참/거짓이 되는 경로를 없앤다. 기존 `fitsLockCard`를 통과해야 하며 이 함수는 폭 추정치일 뿐 실제 화면 검사의 대체물이 아니다. 모호한 이중 부정·복수 명제를 피한다.

확인 문제는 텍스트 상황형 4지선다로 제한한다. 코드 실행·SQL 실행·외부 도구·새 사실 생성은 넣지 않는다. 표현만 바꾼 복제보다 같은 skillKey를 다른 짧은 상황에서 묻는다. 기존 채점 함수가 정답을 비교하며 런타임 AI 채점은 하지 않는다.

## 6. 데이터 설계와 불변 조건

현재 DB user_version은 5다. 다음 충돌 없는 migration에서 아래 의미를 추가한다. JSON payload와 인덱스의 세부 분리는 구현자가 정할 수 있으나 소유권·상태·멱등 제약은 유지한다. DB 오류 시 자동 삭제 금지.

| 저장 영역 | 필수 필드/제약 |
| --- | --- |
| confusion_memories | id, learnerId, subjectId, conceptId, skillKey, summary, status, revision, createdAt, lastEvidenceAt, lastCheckAt. 소유자+과목+개념+skillKey 유일 |
| confusion_evidence | id, memoryId, learnerId, sourceKind, sourceId, sourceVersion, occurredAt, evidenceType. memoryId+sourceKind+sourceId 유일. 원문 전체를 중복 저장하지 않음 |
| generated_questions | 앱이 만든 전역 고유 UUID, learnerId, subjectId, conceptId, memoryId, immutable quiz JSON, kind(gap/check), basisId/version, factIds, promptVersion, model, createdAt, expiresAt, status(pending/approved/rejected/hidden/expired), 검토 결과 |
| personalization_jobs | id, learnerId, subjectId, capturedScope, inputFingerprint, 상태(queued/running/succeeded/failed/cancelled), attemptCount, 시간·오류 코드. 동일 fingerprint 성공 작업 중복 금지. 생성 fingerprint는 memory revision+basis version+대상 날짜+기존 승인/확인 문제 ID 집합을 포함해 다음 확인 문제를 영구 차단하지 않음 |
| personalization_budget | learnerId+localDate 유일, timezone, dispatchCount, pipelineAttempts, gapApprovedCount, checkApprovedCount, checkServedCount |
| personalization_settings | 활성화 여부, 동의 버전/시각. 기존 Settings JSON 확장 가능 |
| 확인 문제 배정 정보 | learnerId+localDate 유일 배정, sessionId/quizId/memoryId, 최초 배정 시각. 재실행 시 같은 미완료 세션 반환 |

- generated quiz ID는 `ai:<UUID>`처럼 기존 `${conceptId}-deep`/term ID와 충돌하지 않게 앱이 만든다. AI가 보낸 소유자·ID·시각·점수는 신뢰하지 않는다.
- 승인 이후 문제 본문·보기·정답은 **불변**이다. 수정은 새 ID로 만든다. 채점·다시 풀기·해상도 재생에 당시 정답을 사용한다.
- 개인 생성 문제를 공유 `quizzes` 테이블에 무소유자 상태로 넣지 않는다. 조회는 learnerId를 반드시 확인한다.
- hidden/expired는 신규 노출 금지다. 과거 기록을 다시 열기 위한 원본은 남긴다. 진행 중인 정상 세션/숨기기 전에 이미 답한 지연 이벤트의 원래 채점까지 임의 변경하지 않는다.
- rejected/미승인 문제는 네이티브 덱·세션에 배정할 수 없다. 숨기기 이후의 새 배정 금지와 과거 이력 조회를 별도 API/옵션으로 구분한다.
- 전체 삭제는 신규 개인 테이블도 cascade 삭제. 현재 기록 초기화는 현재 learner의 전 과목 신규 학습 기록도 삭제한다(기존 resetCurrent 범위 유지).
- 현재 기록 초기화에서는 메모리·문제·작업 등 개인 학습 기록을 지우되, 당일 호출 횟수만 가진 budget 행은 한도 우회를 막기 위해 유지한다. 전체 데이터 삭제는 budget까지 삭제한다. 당일 집계에는 질문·메모리·본문을 넣지 않는다.
- 초기화 뒤 옛 generated UUID의 지연 이벤트는 수용하지 않는다. 메모리·작업·문제의 늦은 저장은 captured learningScope로 거절한다.
- 이미 처리한 근거를 추출 checkpoint로 남긴다. 타임스탬프만으로 dedupe하지 말고 event/message ID를 사용한다.

## 8. 출제와 메모리 갱신 정책

### 8.1 틈새 덱

1. 기존 due/unseen/later 순서와 size 상한을 기본으로 유지한다.
2. 오늘 계획의 focus와 active 메모리는 **같은 우선순위 구간 안의 순서**를 조정한다. 미도래 카드를 overdue보다 앞으로 당기지 않는다.
3. 생성 O/X는 해당 개념이 원래 배정될 자리에 교체해 넣는다. 동일 개념을 여러 장 추가해서 반복량을 늘리지 않는다.
4. 승인·현재 소유자·과목·근거 버전·유효기간·개인화 on 조건을 만족해야 한다.
5. 최종 N에 대해 생성 수≤floor(N/5), 생성 카드는 연속 배치하지 않는다. 못 맞추면 기본 카드를 쓴다.
6. generated gap 항목은 V4에서 잠금 화면/모든 크기 위젯 모두 같은 O/X를 쓴다. 이 항목에서 기존 term/choice로 자동 교체하지 않는다. 다른 기본 카드의 위젯 변형은 유지한다.
7. 생성된 개념의 복습 일정은 기존 gap_progress를 사용한다. 동일 이벤트의 해상도 가산은 1번, 기존 틈새 O/X 가중치 유지.

계획 날짜를 네이티브가 AI로 판단하지 않는다. 앱에서 configure한 덱을 오프라인 사용한다. 앱을 오래 열지 않아 지난 계획의 순서가 남을 수 있다. 생성 질문은 각 항목에 expiresAt을 전달해 native도 만료된 생성 항목을 건너뛴다. 적합한 항목이 없으면 안전한 기존 빈 상태로 돌아가고 앱 재개 때 다시 구성한다.

### 8.2 확인 문제

- active 또는 improving 메모리, 해당 생성 카드의 실제 응답, 24시간/다른 날짜 조건을 모두 충족하면 후보가 된다.
- 정답/오답 어느 쪽이든 틈새에서 응답한 뒤 확인 기회를 만들 수 있다. 노출만 된 카드는 조건을 충족하지 않는다.
- 하루 목표 중 남은 한 자리를 쓴다. 기존 미완료 세션을 먼저 끝내고, 정상 채점 가능한 개념에만 배정한다. 가능한 후보가 없으면 기본 문제.
- 일일 확인 배정은 DB에서 원자적으로 한 번 생성한다. 앱을 닫거나 답을 보지 않고 나가도 새 확인 문제를 추가 배정하지 않는다. 날짜가 바뀌어 미완료 확인을 재개하면 그 날짜 슬롯을 차지하고 추가 배정을 막는다.
- 확인 문제는 정상 app 문제와 같은 가중치/채점 규칙을 사용한다. 반복 연습·다시 풀기는 메모리 해결 조건의 독립 정답으로 세지 않는다.
- improving 상태에서 두 번째 확인이 필요하면 같은 생성 카드에 다시 답하도록 강요하지 않고 기존 응답 근거를 재사용할 수 있다. 이전 확인과 다른 문제·다른 날짜·24시간 간격을 요구한다.
- resolved된 메모리의 생성 카드는 다음 sync부터 신규 덱에서 제외한다. 해당 기록/문제는 보존한다.

## 9. AI 실행·우선순위·취소

새 서비스 후보: `src/services/ai/personalization.ts`, `requestCoordinator.ts`. 메모리/정책 순수 함수는 `src/domain/personalization.ts`로 분리한다. 기존 complete를 공통화하되 ID 소유권·늦은 bridge promise 처리를 잃지 않는다.

- 모든 SIWC 응답 요청은 앱 단위 조정기 하나를 통과한다. native의 response_busy 거절은 마지막 보호 장치로 남긴다.
- 우선순위: **사용자가 보낸 채팅 > 필요한 7일 계획 > 메모리·콘텐츠 준비**.
- foreground에서 마지막 학습/대화 완료 뒤 30초 idle, 처리할 새 근거/필요 확인 문제가 있고 동의·연결·모델이 유효할 때 준비한다. 매 렌더·매 snapshot revision마다 호출하지 않는다.
- 사용자가 채팅을 보내면 낮은 우선순위 작업을 해당 작업의 ID로 취소하고 terminal 종료를 기다린 뒤 시작한다. 아직 ID가 안 왔다면 promise 도착 시 그 ID만 취소한다. 채팅을 취소하거나 다른 작업 ID를 재사용하지 않는다.
- 백그라운드 전환, 로그아웃/프로필·과목 전환, 초기화, 개인화 끄기/동의 철회 시 자동 작업을 취소한다. 강제 종료된 running 작업은 다음 실행에서 실패/취소 상태로 회수하고 성공으로 복원하지 않는다.
- 일일 파이프라인/dispatch 예약은 취소·실패에도 환불하지 않는다. 호출을 시작하기 전 ready/busy 확인으로 불필요한 예약을 줄이고, 사용자 채팅은 자동 작업 예산과 무관하게 동작한다.
- 각 요청의 before dispatch / completed / save 직전에 learnerId, subjectId, learningScope, 동의 버전을 확인한다. 다른 과목으로 갔다가 돌아온 경우도 옛 결과를 살리지 않는다.
- 메모리 revision·basis version이 처리 중 바뀌면 해당 후보 저장을 거절하고 새 입력 작업으로 넘긴다. 날짜 경계에서는 완료 시점 한도도 재확인한다.
- 90초 timeout을 기본으로 사용한다. completed 전 스트리밍 JSON은 카드·메모리로 저장하지 않는다.
- auth 만료·사용량 제한은 재시도 루프 없이 기본 학습 유지. 기존 연결/사용량 화면에서 확인 가능하게 한다. 토큰 수를 구독 잔량으로 표시하지 않는다.
- 한 작업에서 결과 일부만 유효하면 유효한 후보만 한도 내 승인한다. 검토 응답이 전체 실패하면 어느 후보도 승인하지 않는다.
- 메모리만 새로 저장됐다면 plan을 dirty 표시하되 즉시 연쇄 요청하지 않는다. 하루 자동 갱신 최대 1회, 마지막 계획 요청 후 최소 10분, idle 상태에서 갱신한다. 새 근거가 없으면 기존 needsPlan 동작만 유지한다.

## 10. AI 입출력 계약

JSON은 raw 응답을 곧바로 TypeScript 타입으로 단언하지 말고 런타임에서 검사한다. 사용자 대화·콘텐츠 안의 명령은 자료로 취급한다.

메모리 추출 응답(예시 형태):

```json
{
  "candidates": [{
    "conceptId": "ds-queue",
    "skillKey": "queue-order",
    "summary": "스택과 큐의 꺼내는 순서를 혼동했을 가능성",
    "evidenceRefs": ["attempt:existing-id"],
    "kind": "wrong-choice"
  }]
}
```

- evidenceRefs는 이번 입력에 실제 제공한 ID만 허용한다. summary 최대 120자. 입력 사실을 초과하면 폐기.
- 후보 0개가 정상 결과다. 질문이 있었다는 이유만으로 후보를 채우도록 강제하지 않는다.
- 입력에서 제공한 기존 memoryId를 함께 줄 수 있으나 업데이트 대상 소유권·개념·skillKey를 앱이 다시 확인한다.

콘텐츠 후보 응답:

```json
{
  "gap": [{
    "memoryId": "input-memory-id",
    "conceptId": "ds-queue",
    "basisId": "input-basis-id",
    "factIds": ["input-fact-id"],
    "prompt": "큐는 먼저 넣은 것을 먼저 꺼낸다.",
    "answer": "o",
    "explanation": "기준 자료의 FIFO 규칙을 짧게 설명한다."
  }],
  "checks": []
}
```

- 예시는 형식 설명이며 그대로 production 카드로 등록하지 않는다. gap prompt≤80자이면서 fitsLockCard, explanation≤120자, 줄바꿈 없는 단일 명제를 기본으로 한다.
- checks는 memoryId/conceptId/basisId/factIds, prompt≤180자, context≤300자(optional), options 4개(각≤80자·고유 id/text), correctOptionId, explanation≤300자. 한 개만 허용.
- generated 질문의 sourceRefs는 승인된 basis에서 앱이 구성한다. 모델이 출처 URL·checkedAt·승인 상태를 채우지 않는다.
- 정규화된 prompt/options 해시로 같은 학습자·과목 안의 동일 후보를 중복 승인하지 않는다. quota를 채우기 위한 무한 재생성 없음.

## 11. 화면·동의·삭제

- 설정에 “AI 맞춤 학습” 스위치 한 행과 짧은 설명: “오답과 이 앱의 대화를 바탕으로 카드와 확인 문제를 준비해요.” 앱 내 기록만 사용하며 다른 ChatGPT 대화/메모리를 가져오지 않는다.
- 기존 사용자는 기본 off로 migration한다. AI 전송 동의가 있어도 신규 자동 개인화는 명시적으로 켠 뒤 시작한다. 신규 사용자도 기존 AI 안내에 이 용도를 명시하고 선택할 수 있게 한다. 별도 긴 온보딩을 추가하지 않는다.
- 끄면 생성/메모리 추출을 취소하고 generated 신규 출제·덱 편입을 중지, native 덱을 기본 카드로 갱신한다. 이미 남은 기록은 조회할 수 있고 명시적 기록 초기화/삭제 시 함께 삭제된다. 기존 수동 채팅·기본 계획 동의와 구분한다.
- AI 생성 카드/확인 문제에는 작은 `AI` 텍스트 표시와 접근성 설명을 둔다. 기본 콘텐츠도 AI 작성 초안이라는 기존 안내는 유지한다. 아이콘/색만으로 생성 출처를 표시하지 않는다.
- 새 표시는 잠금 화면의 두 줄 문제 공간을 빼앗지 않게 기존 영역 라벨 옆에 둔다. 실제 최소 폭/큰 글씨에서 잘리면 장식을 먼저 줄인다.
- 개념 상세에 “자주 헷갈린 점” 진입점, 상태와 짧은 요약, 무시/삭제 제공. 생성 카드 상세에는 기준 자료와 “이 카드 숨기기”를 제공한다.
- 숨기기는 withGapLock을 거쳐 DB commit→native 덱 재구성 순서. 사용자 채점 직전/직후의 지연 이벤트는 기존 트랜잭션·원본 규칙대로 처리한다.
- 잠금 화면에는 학습 내용만 표시한다. 개인 질문 원문, 인용 발언, “당신은 어제 …라고 했어요” 같은 개인 맥락을 넣지 않는다.
- 실패는 설정/상세에서 “맞춤 카드를 준비하지 못했어요. 기본 카드로 이어가요.” 정도로 조용히 표시한다. 오류 팝업 반복·새 챗봇 화면·계획 이유 문장 부활 없음.
- UI 구현 시 설치된 UI UX Pro Max와 Impeccable의 네이티브 지침을 읽고 기존 DESIGN과 사용자 선호를 우선한다.

## 13. 필수 자동 검증 사례

### 데이터·상태

- v5에 학습/대화/프로필이 있는 DB migration 후 기존 기록 보존. migration 실패 시 rollback.
- 같은 오답 이벤트를 두 번 ingest해도 evidence·상태·해상도가 한 번만 변함.
- 질문만 한 사용자에게 오개념을 만들어 넣지 않음. assistant 발언만 참조한 후보 거절.
- 확인 정답 1회는 improving, 다른 날짜·문제 2회만 resolved. 중간 오답은 active로 복귀. practice/재탭 제외.
- generated quiz 원본을 만료/숨김 뒤에도 과거 기록·다시 풀기에서 동일하게 조회. 타 learner의 UUID로 조회/채점 실패.
- 초기화·과목/프로필 왕복·개인화 끄기 후 지연 완료가 신규 메모리/카드/계획을 부활시키지 않음.
- 숨긴 메모리의 같은 evidence가 새 분석에서 재등장하지 않음. 새 근거와 구분.

### AI·사용량

- 미등록 concept/skill/fact/evidence ID, 잘못된 정답 ID, 모호한 검토, prompt injection, 중복 후보, 길이 초과 거절.
- 생성자가 낸 답과 독립 검토 답 불일치, timeout/failed/cancelled/부분 stream에서 승인 0개.
- 같은 fingerprint 성공 작업은 다시 dispatch되지 않음. 재시작·과목 변경으로 일일 한도 우회되지 않음.
- 작업 중 채팅 우선 전환 시 자기 요청만 취소, late start ID 처리, 새 채팅이 계획 JSON을 받거나 저장하지 않음.

### 학습 흐름·네이티브

- 최종 N이 1/4/5/10/30인 덱에서 비율 상한, 생성 연속 배치 없음, overdue 우선 유지.
- 생성 항목의 위젯이 기본 term으로 바뀌지 않음. origin/expiry가 Kotlin 저장·복구에서 유지되고 만료 항목을 건너뜀.
- generated gap 응답을 올바른 learner로 ingest하고 commit 전에 native ack하지 않음. commit 후 crash/replay도 중복 없음.
- 첫 확인 24시간/다른 날짜 조건, 목표 완료 후 강제 추가 없음, 미완료 세션 재개·자정 경계에서도 하루 1문제.
- generated unavailable/개인화 off/연결 없음/사용량 제한에서도 기본 학습·덱이 동작.
- API36 세로 고정, 360/412dp·100/200%에서 AI 표시·O/X·숨기기·확인 문제 선택지 접근. 시스템 알림/위젯의 실제 폭도 별도로 확인.

기존 `npm run check`, 관련 Kotlin/JUnit, debug/AndroidTest 빌드를 유지한다. 보호할 데이터가 있는 에뮬레이터에서 DB를 지우는 native-smoke를 실행하지 않는다. 새 기능 fixture는 별도 테스트 DB/격리된 테스트 경로로 검증하고 production 모의 성공 스위치를 넣지 않는다.

실제 SIWC가 환경/계정 조건상 실행되지 않으면 fixture 검증과 실제 completed 결과를 분리해 기록한다. 이번 계획의 완료 기준에 사용자에게 로그인·실기기 조작·다인 테스트를 요구하지 않는다.

## 14. 완료와 인계

V4 완료에는 다음이 모두 연결되어야 한다.

- [x] 근거를 가진 메모리가 저장되고 다음 AI 요청에 실제 사용됨. (fixture 자동 검증, 실제 계정 미검증)
- [x] 승인 생성 카드가 네이티브 덱에서 답변 가능하며 기록·해상도·다시 풀기로 연결됨. (JS·Kotlin 자동 검증, 실기기 표시 미검증)
- [x] 확인 문제 결과가 메모리 상태와 다음 출제에 반영됨.
- [x] 하루 생성/노출 한도, 계정/과목 격리, 취소·초기화·숨김·만료 처리 검증됨.
- [ ] AI 생성 표시·기준 자료·개인화 끄기·기록 삭제가 실제 동작함. (구현·자동 검증, 설정 켜기/끄기만 기기 확인. 실제 AI 카드 화면은 미확인)
- [x] AI 없이 기본 기능 유지, 기존 세로 고정·크래시 패치·상태 전이 수정 유지.
- [x] WORK_LOG/VERIFICATION/README에 구현됨·자동 검증됨·실제 계정/기기 미검증을 나눠 기록.

인계 시 “메모리→생성 카드→실제 응답→확인→메모리 갱신” 한 시나리오의 이벤트 ID/상태 변화 증거를 남긴다. 사용자 내용·토큰을 공개 로그에 남기지 않는다. 실제 사용자 수·교육 효과·과제 인정 여부는 자동 검사 결과로 대신 주장하지 않는다.
