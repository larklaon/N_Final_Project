## 2026-10-18 — V4.C3 — 공통 요청 조정기 · 생성 · 별도 검토

- `requestCoordinator`: 앱 전체에서 SIWC 응답 하나만. 우선순위 채팅 > 7일 계획 > 개인화 준비. 높은 순위가 오면 낮은 순위 요청을 그 요청의 id로 취소하고 네이티브 종료 이벤트(없으면 3초)를 기다린 뒤 시작한다. 채팅 중에는 배경 작업이 기다린다. 늦게 온 시작 id는 자기 것만 취소, 다른 요청의 이벤트는 무시. 네이티브 response_busy는 마지막 보호로 남긴다. 7일 계획 요청과 채팅 화면이 이 조정기를 쓰도록 바꿨다(기존 계획 테스트 그대로 통과).
- 생성 계약(`contentInstructions`·`parseContentCandidates`): target의 memory·개념·skill·기준 사실만. gap은 80자·한 줄·두 줄 맞춤(`fitsLockCard`)·이중 부정/여러 명제 금지·답 o/x·설명 120자, check는 하나만·질문 180자·상황 300자·보기 4개(고유 id·문구, 80자)·정답 id 확인. URL·코드 블록·꺾쇠는 거절.
- 독립 검토(`reviewInput`·`approvedByReview`): 검토자에게는 문제와 기준 사실(조건 포함)만, 생성자의 답은 숨긴다. 같은 답·supported·근거 fact 인용 셋 다 맞아야 승인. 검토 응답이 깨지면 승인 0. 두 모델의 동의는 자동 검사일 뿐 전문가 검수가 아니다.
- 파이프라인(`runPersonalization`): 개인화 on·동의·연결·모델 확인 → 중단된 running 작업은 실패로 회수 → 오래된 메모리 archived, 만료 처리 → 새 근거·대상 없으면 건너뜀 → 같은 입력 fingerprint 성공 작업은 다시 안 함 → 하루 2회·요청 6회 예약(환불 없음) → 추출 → 생성 → 검토 → 한도 안에서 승인 저장. 각 요청 전후에 학습자·과목·scope·동의 재확인, 바뀌면 cancelled. 실패 뒤 10분 안에는 다시 하지 않는다. 메모리가 바뀌면 계획을 dirty로만 표시(즉시 연쇄 요청 없음).
- 실행(`PersonalizationRunner`): 앱이 앞에 있을 때 마지막 학습 변화 30초 뒤 한 번. 백그라운드 전환·scope 변경·끄기에서 취소.
- 검증: Jest 123(신규 11: 오답→메모리→승인 카드·같은 입력 재실행 없음·검토자에게 답 숨김, 다른 답/애매/깨진 검토 승인 0, 추출 실패·취소 저장 0, 처리 중 초기화 저장 0, 끔·미연결 전송 0, 하루 2회, 채팅 선점(자기 id만 취소·채팅 중 대기), 생성 출력 검사)·lint·콘텐츠. 실제 ChatGPT 응답으로는 아직 돌려 보지 않았다.

## 2026-10-18 — V4.C2 — 근거 · 헷갈림 메모리

- 근거 조회(`extractionInput`): 최근 14일의 채점된 앱 오답(선택 보기 포함, 전용 조회)과 틈새 오답, 답이 끝난 학습자 채팅 발언(직전 assistant 답은 맥락으로만, 최대 20개·8,000자). V4 기준 자료 4개념만, 처리한 근거(checkpoint, event/message id)는 다시 보내지 않는다. 답이 오지 않은(실패·취소·진행 중) 발언은 뺀다.
- 추출 계약(`memoryInstructions`, `parseMemoryCandidates`): 알려진 개념·skill, 이번 입력에 실제로 넣은 ref만, summary 120자·한 줄, wrong-choice는 오답 근거 필요, learner-statement는 학습자 본인의 단순 질문이 아닌 발언 필요(추천 칩·8자 미만은 질문으로 본다). 후보 0개는 정상. 짝 skill(스택–큐)은 양쪽 개념의 근거를 인정한다.
- 상태(`memoryStatus`, 앱 코드가 계산): 오답 1건은 candidate, 서로 다른 문제 2건·같은 문제 다른 날짜·명확한 발언은 active. 마지막 오답 이후 확인 정답 1회는 improving, 다른 날짜·다른 문제·24시간 간격 2회는 resolved, 새 오답은 active로 복귀. AI confidence는 쓰지 않는다.
- 저장(`applyCandidates`): 소유자·scope·과목 재확인, 개념당 열린 메모리 3개, 근거는 memoryId+출처 유일, 보낸 근거 전부 checkpoint. 무시(`ignoreMemory`)하면 archived로 두고 그 근거를 ignored로 표시해 재사용을 막는다. 새 근거가 오면 candidate부터 다시. 30일 소식 없는 메모리는 archived(resolved와 별개).
- 아직 개발 중인 v6 스키마의 confusion_evidence에 quizId·localDate를 더했다(에뮬레이터 DB는 v5 그대로라 영향 없음).
- 검증: Jest 112(신규 8: 근거 범위·미완료 발언 제외, 가짜 ref·단순 질문·모르는 skill·긴 요약·비JSON 거절, 중복 적용 1회, 상태 전이 표, 발언 단독 active, 무시 후 재사용 금지·새 근거로 재시작, 30일 archived, 초기화 뒤 옛 작업 거절)·lint·콘텐츠.

## 2026-10-18 — V4.C1 — 기준 자료 · 저장 구조

- 기준 자료 대조(개발자 확인, 전문가 검수 아님): 공식 문서를 직접 읽고 `src/data/content/generation-basis.json`(basisId `v4-basis` v1)에 사실을 요약했다.
  - Python Tutorial 5.1.1/5.1.2: 스택은 마지막에 넣은 것을 먼저 꺼낸다(LIFO), 큐는 먼저 넣은 것을 먼저 꺼낸다(FIFO), 넣고 꺼내는 끝.
  - PostgreSQL 5.5.4/5.5.5: 기본키는 유일·NOT NULL, 여러 열 가능, 테이블당 최대 하나. 외래키 값은 참조 테이블의 행과 일치(참조 무결성), 기본키뿐 아니라 유일 제약 열도 참조 가능(PostgreSQL 기준으로 조건 명시).
  - 외래키 열의 NULL 처리는 MATCH 옵션·DBMS에 따라 달라 `excluded`로 두고 어떤 skill에도 넣지 않았다.
  - skill: `stack-queue-order`(스택·큐 공통), `pk-rules`, `fk-rules`, `pk-fk-role`. 짝 헷갈림이 양쪽 사실을 인용할 수 있게 사실은 기준 자료 전체에서 찾는다. 기존 catalog의 `ai-draft`/`출처 대조 전` 표시는 바꾸지 않았다.
- DB v6(`v6Schema`): confusion_memories(소유자+과목+개념+skillKey 유일), confusion_evidence(memoryId+sourceKind+sourceId 유일), evidence_checkpoints, generated_questions(소유자 필수, 내용 해시 중복 금지, 승인 후 불변), personalization_jobs(같은 입력 성공 중복 금지), personalization_budget(학습자+날짜), check_assignments(학습자+날짜). 마이그레이션은 트랜잭션, 더 새 DB는 열지 않는다.
- 설정: `personalizationEnabled`(기본 off), 동의 시각·버전. 기존 AI 전송 동의와 별개.
- `PersonalizationStore`: 한도 예약(넘으면 거절, 환불 없음), 승인 문제 저장(현재 학습자·learningScope·과목 확인, 하루 승인 한도, 정규화 해시 중복 거절, 근거 사실은 승인된 것만, `ai:<UUID>` id, 출처는 기준 자료에서 앱이 구성, 잠금 화면 short = prompt), 소유자 확인 조회, 숨기기·만료, 초기화(한도 행은 유지). 전체 삭제는 학습자 cascade로 한도까지 지운다.
- `quiz()`와 틈새 응답 수집은 `ai:` 문제를 이벤트 주인 학습자로만 찾는다.
- 검증: typecheck·lint·Jest 104(신규 7: v5→v6 보존, 새 DB 거절, 기준 자료 승인/제외, 한도·재실행·초기화·삭제, 소유·중복·한도·불변, 과목 왕복 뒤 옛 작업 거절, 미승인 사실 거절)·콘텐츠. 마이그레이션 실패 rollback은 트랜잭션에 기대며 실패 주입 테스트는 없다.
